# 后训练数据产品速查（来自四条采购帖）

## 先看全局：这些数据用在训练的哪一步

预训练（海量语料）→ SFT（示范：教模型怎么答）→ 偏好 / 奖励（比较：教模型哪个更好）→ RL（在任务或环境里试错，按规则、Rubric 或验证器打分）→ 评测（Benchmark、LLM-as-a-Judge，检验效果）

越往后，越依赖专家判断，单价越高、越难被合成数据替代。我们的位置在后三段。

## 逐项说明

### 1. 高质量 SFT 指令数据
- **是什么**：一问一答的示范，教模型"这种问题该这样答"。
- **一条长什么样**：`{instruction, input, output}`，output 由专家写或专家改写。
- **买方看重**：问题难、答案对、风格统一；"拒绝模板批量生成"（帖 3）说的就是不要一个模板换几个词批量造。
- **难点**：专家时间。越专业的领域，每条越贵。

### 2. 复杂 Prompt / Query 构造
- **是什么**：专门出难题，是其他数据（SFT、Rubric、评测）的起点。
- **一条长什么样**：一个真实场景的多约束问题，例如"给定这家公司三年财报，计算自由现金流变化，判断分红是否可持续，并指出两个风险点"。
- **买方看重**：像真实用户问的、模型现在答不好、不是众包凑的（帖 1 原话"不是简单众包"）。

### 3. Reference Answer / Response 生成
- **是什么**：为难题写标准答案或高分答案，供 SFT 使用或作为 Rubric 打分的参照。
- **买方看重**：正确、完整、可验证；金融题要算对数。

### 4. CoT 思维链推理数据
- **是什么**：不只给答案，还写出一步步推理过程。
- **一条长什么样**：问题 → 推理步骤 1…n → 结论。
- **买方看重**：每一步都对、没有跳步；数学、金融计算最常见。

### 5. 代码 SFT / 代码调试指令
- **是什么**：代码 SFT 是"需求 → 正确代码"；调试指令是"有 bug 的代码 + 报错 → 定位原因 → 修复"。
- **买方看重**：代码能跑、有测试、贴近真实工程（不是刷题），附修复思路。
- **我们**：软件工程环境里"代码能否挺过下一个版本"正好对应。

### 6. 代码预训练语料
- **是什么**：大量高质量代码文本（仓库、文档），用于预训练。
- **注意**：拼的是量、来源和许可证，不需要专家，单价低。不是我们的定位，接单的话找渠道伙伴分包。

### 7. RLHF 人类偏好数据
- **是什么**：同一问题的两个或多个回答，由人判断哪个更好，常附理由和分维度评分。
- **一条长什么样**：`{prompt, response_a, response_b, chosen, reason}`。
- **用途**：训练奖励模型（Reward Model），或直接用于 DPO 一类方法。
- **买方看重**：标注一致性（不同专家判断是否一致）、理由写得清楚。

### 8. Reward 数据
- **是什么**：给回答打分（绝对分或排序），用于训练或校准奖励模型；和偏好数据是一家。

### 9. Rubric 设计与拆解
- **是什么**：把"好答案"拆成可逐条检查的评分项。现在做 RL 的主流做法之一：没有标准答案的任务，用 Rubric 当奖励。
- **一条长什么样**：
  - 题目：分析某公司 Q2 财报，给出评级建议
  - 评分项：① 毛利率变化算对（3 分）② 指出存货周转恶化（2 分）③ 结论和数据一致（3 分）④ 编造数据（−5 分）
- **买方看重**：评分项具体、不含糊、覆盖关键点，而且模型没法钻空子。
- **我们的卖点**：评分标准上线前做对抗测试（月结环境评分漏洞 6 → 0）。

### 10. Rubric 逐项评分与质检
- **是什么**：拿 Rubric 给模型的回答逐项打分，再抽检复核。
- **买方看重**：打分一致、质检流程成熟（帖 1 第 3 条），通常要看抽检合格率。

### 11. LLM-as-a-Judge 评测数据
- **是什么**：用人类专家的打分去训练或校准"让大模型当裁判"的评测器。
- **一条长什么样**：回答 + Rubric + 专家逐项分数 + 理由；用来检验模型裁判和专家的一致率。
- **买方看重**：专家分数可靠，覆盖难例和边界情况。

### 12. 模型评测 / Benchmark
- **是什么**：一套固定的难题加评分方法，用来比较模型；分公开和私有（不外泄，防止刷榜）。
- **我们**：Xitadel（交易）、MLBench（AI 研究）、未来预测、谜题基准。

### 13. RL 任务 / RL 环境与验证器
- **是什么**：模型在环境里做事，由规则或验证器自动打分，分数直接当奖励。
- **一条长什么样**：任务描述 + 可交互环境（沙箱、工具、数据）+ 验证器（判断结果对不对）。
- **买方看重**：验证器不能被钻空子（reward hacking）、任务够难、可批量跑。
- **我们的卖点**：谜题基准 400 次作弊攻击 0 次成功；Xitadel 训练后交易表现 +12%。

### 14. Agent 工具调用 / 多轮交互轨迹
- **是什么**：记录 Agent 完成一个任务的全过程：用户说了什么、模型怎么想、调了什么工具、工具返回什么、最后结果。
- **一条长什么样**：一个 Session = 多轮 `[用户消息 → 模型思考 → tool_call{名称, 参数} → tool_result → …] → 最终回答`，附元数据（模型、工具数、轮数、是否成功）。
- **买方看重**：任务长（帖 2 要求每个 Session ≥30 次 Tool Call）、过程完整、真实。

### 15. 金融 Agent 真实轨迹（帖 2 的具体规格）
- 每个 Session 至少 30 次 Tool Call，至少 5 轮真人对话。
- 必须是真实使用中产生的日志，不收纯合成数据。
- 要完整 Session：工具输入输出和中间过程全保留。
- 模型限定为 Claude Opus 4.8 以上、GPT-5.6、Kimi K3、GLM-5.2 以上。
- **合规前提**：
  - 只能用我们自己专家、经本人同意产生的记录。
  - Anthropic 和 OpenAI 的条款禁止用它们的输出训练别的模型，要先和买方说清楚。

### 16. DeepResearch 数据
- **是什么**：长时间检索加综合的研究任务，例如"调研某行业竞争格局并写报告"。包括题目、检索轨迹、引用来源和最终报告，常配 Rubric 评分。
- **买方看重**：题目有深度、引用真实、报告结论可核查。金融研究是我们的天然场景。

### 17. 多模态训练数据（图片、视频、音频、多语种）
- **是什么**：采集加标注，拼源头资源和人力规模。
- **注意**：不是我们的定位；帖 4 那类数据公司正好有，可以互相分包。

## 买方共同的验收习惯

- **先小批量 Demo 或样例**：四条帖子里三条明说了。
- **可提供脱敏样本**，供内部测评（帖 3）。
- **稳定批量交付**：看团队规模和质检流程。
- **技术团队懂 RL、SFT、LLM-as-a-Judge**：能听懂需求、能对齐格式（帖 1）。
- **不要低价流水线外包**（帖 3）：这正好是我们要打的点，靠专家和质检取胜，不拼价格。
